# Unified acquisition (Milestone 008)

Open `/acquisition` → **Discover**. Choose Remotive, Overture or HN, run explicitly, review evidence/unknowns and save selected findings. Source, pipeline, arrangement, geography, skill, publication freshness and lifecycle filters work on normalized records. Filters do not trigger provider requests. **Sources** shows all nine requested categories, honest provider setup/status, documentation/conditions and recorded run yield/errors. **Clients** links to existing CRM/research; **Remote Jobs** is an application worklist, never a sales-pitch queue. **Agency Partnerships** is an operator-chosen hypothesis until actual demand is documented. Research remains separate. No automatic messages/applications or background discovery.

## Source assessment

Two remote sources assessed before coding:

- **Remotive selected:** [official API documentation and conditions](https://github.com/remotive-com/remote-jobs-api). Free public JSON, no API key/billing. Attribution and links to Remotive listings required; 24-hour delay. Do not submit their jobs to other job boards, or gate listings behind signup/email collection. Documentation advises at most four requests/day and blocks more than two/minute. This localhost tool uses a six-hour ignored local cache, a persistent rolling limit of four network attempts/day (including failures), minimum one-minute retries and a database advisory lock. No public job dataset is published. Selected snapshots stay private in Neon; recheck active listings and provider conditions before applying or any future redistribution.
- **Remote OK not integrated:** its [public API](https://remoteok.com/api) exposes attribution/link-back conditions in the response. Public access was available, but sampled geography was often missing or embedded in descriptions. Remotive's candidate-location and employment fields provided a simpler first vertical slice. No claim of unrestricted reuse, quota or broader permissions is made for Remote OK.

Remotive uses one fixed documented engineering-category API URL, refuses redirects, enforces JSON/schema, 30-second deadline, 12 MiB response cap and 2,000-record cap. The actual API response included non-engineering listings despite the category parameter; local rules exclude incidental technology tags on administrative, sales, annotation and writing roles. Provider availability is not commercial success. Errors remain errors, not fabricated empty results.

Overture and HN retain their existing access, size/time limits, domain restrictions and source conditions; no new scraping. Official websites use the existing explicit single-page research flow. Future Google Places, Reddit, YouTube, Apollo, GitHub, LinkedIn, news and project-feed entries are **not connected**; access/credentials/quotas/retention must be assessed before implementation. Registry documentation is not permission to access those services. Existing GitHub/Git access or an external Apollo connector does not connect them to HassanOS.

## Normalization and identity

The shared record retains provider/source ID and URL, source publication and retrieval dates, identity assertions, original plain-text evidence, classification, work arrangements, geography/eligibility evidence, relevant skills, published salary/currency, seniority indicator, timezone/authorization restrictions, deadline, competition (unknown unless supplied), route purpose, lifecycle, missing information and next action. Original source facts are separate from AI inference; no model is needed to extract fixed API fields. Existing local Qwen remains available through the selected business/HN research handoff. No experience, applicant counts, contacts, employer domains or buying intent are manufactured.

All requested arrangements are representable; unknown and multiple types are supported. A bare provider `contract` remains `contract_unspecified`, not an invented independent/fixed-term classification. Published timestamps without offsets use UTC for sorting, with original calendar date retained. Seniority is only a title indicator, not an automatic exclusion or a verified qualifications match. Engineering relevance uses source content plus skills; unrelated roles are not included merely because tags say React/REST.

Worldwide/APAC/EMEA advertising is **not** confirmed Pakistan eligibility. Only explicit Pakistan candidate-location evidence produces the `confirmed` flag in this first adapter, subject to contradictions/exclusions. Country/region restrictions are retained and presented. No claim is made that Hassan meets years of experience, authorization, licensing, leadership or timezone requirements. Salary strings are retained verbatim; `$` alone does not establish USD. Missing compensation/currency/deadline/competition remain unknown. A provider-active listing is `current_unconfirmed`, not employer-verified; old, closed and explicitly expired records are flagged.

Migration `0006` adds three tables: acquisition identities, selected findings and run metadata. `0007` scopes URL uniqueness to record-specific URLs and backfills URL scope, so unrelated records sharing a catalogue index are not merged. Existing CRM/research/drafts are untouched. Jobs cannot be saved as client sales, and catalogue records cannot be labelled jobs without hiring evidence. Reclassifying research as a client/partnership explicitly remains an operator hypothesis. Selected Overture/HN saves can reuse their existing campaign research handoff; no automatic CRM lead is created. Jobs have no such handoff.

Provider IDs, exact canonical source URLs and source-asserted canonical domains resolve identities deterministically. No fuzzy name merging or domain inference from employer names. Shared platform/social domains are excluded. Where a job feed supplies no employer domain or stable employer ID, repeated employer names remain unresolved rather than being automatically merged. Name equality alone is not a verified identifier; manual resolution is future work. A source-asserted domain can be wrong: inspect provenance and resolve conflicts manually. Multiple openings and different pipelines can share an organization while retaining separate finding records. Duplicate saves preserve the first selected evidence and pipeline, append source aliases and update last-seen; they do not overwrite existing CRM/research. Later source refresh/reclassification and manual identity-conflict resolution are intentionally not built yet.
